> ### Нефункциональные требования
>
> * Отвечать на запрос публикации после загрузки фотографии за p95 не более 500 мс и p99 не более 1 с.
> * Новая публикация должна появиться в ленте подписчика в течение 60 секунд в обычной ситуации.
> * Первая страница ленты с метаданными должна отвечать за p95 не дольше 300 мс и p99 не дольше 1 с при расчётной пиковой нагрузке. Время загрузки изображения измеряется отдельно.
> * За скользящие 30 дней не менее 99,95% допустимых запросов ленты должны завершаться корректным ответом; для публикации — не менее 99,9%. Ответ, молча потерявший часть доступных публикаций, не считается корректным. Эти целевые значения — вводные учебного кейса, их стоимость и достижимость можно обсудить.
> * Подтверждённая публикация не должна навсегда теряться при сбое. Дубликатов в ленте быть не должно.
> * После отписки или удаления пост исчезает из новых ответов ленты в течение минуты.
>
> ### Данные по использованию
>
> * 50 млн зарегистрированных пользователей; 10 млн активных пользователей в день.
> * 2 млн новых постов и 100 млн запросов главной ленты в день.
> * У обычного автора около 200 подписчиков. Есть авторы с десятками миллионов подписчиков; у одного из них 20 млн, он публикует 1–3 поста в день.
> * Для предварительной оценки пика принять нагрузку в 10 раз выше среднесуточной частоты.
> * Первая страница содержит 20 постов; основной сценарий — первые несколько страниц.

> ### Что спроектировал и сделал коллега
>
> 1. `Post Service` сохраняет пост в своей базе и синхронно вызывает `Feed Service.distribute(post_id, author_id)`. Ответ автору возвращается только после ответа `Feed Service`.
> 2. `Feed Service` получает подписчиков через `Follows Service` и добавляет ссылку на пост в ленту каждого подписчика. `Feed Entries` хранит строки `(viewer_id, created_at, post_id)` в течение 30 дней.
> 3. При чтении `Feed Service` выбирает очередные 20 ссылок через `OFFSET` и запрашивает метаданные постов у `Post Service`.
> 4. При отписке удаляется связь в `Follows Service`, при удалении поста — запись в `Posts DB`. Что делать со ссылками, уже попавшими в ленты, коллега пока не описал.
>
> Есть локальный прототип: публикация и чтение ленты работают на небольшом наборе данных. Очереди и кеша в текущем проекте нет.
>
> ```plantuml
> @startuml
> top to bottom direction
> rectangle "Клиент" as Client
> rectangle "Post Service" as PostService
> database "Posts DB" as Posts
> rectangle "Follows Service" as Follows
> database "Feed Entries" as Entries
> rectangle "Feed Service" as FeedService
>
> Client --> PostService : публикует
> PostService --> Posts : сохраняет пост
> PostService --> FeedService : distribute(post_id) синхронно
> FeedService --> Follows : получает подписчиков
> FeedService --> Entries : пишет каждому до ответа
> Client --> FeedService : читает ленту
> FeedService --> Entries : 20 ID через OFFSET
> FeedService --> PostService : загружает метаданные
> @enduml
> ```
>
> Фрагмент прототипа:
>
> ```python
> class PostService:
>     def publish(self, author_id, media_ref, caption):
>         post = posts.insert(author_id, media_ref, caption)
>         feed_service.distribute(post.id, author_id, post.created_at)
>         return post.id
>
> class FeedService:
>     def distribute(self, post_id, author_id, created_at):
>         for viewer_id in follows_service.all_followers(author_id):
>             feed_entries.insert(viewer_id, created_at, post_id)
>
>     def get_feed(self, viewer_id, page, size=20):
>         ids = feed_entries.query(viewer_id, offset=page * size, limit=size)
>         return post_service.get_many(ids)
> ```
