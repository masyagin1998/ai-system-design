# План MVP: публикации и главная лента

Полный контекст и требования — [spec.md](spec.md). MVP демонстрирует публикацию метаданных,
подписки, удаление и смешанную сборку ленты в одном FastAPI-приложении с PostgreSQL и Redis.
Ручка публикации сначала сохраняет фотографию в RustFS, затем сохраняет пост и outbox-событие.

## 0. Перемычка: prod → MVP

- Оставляем: пользователей, подписки, посты, выдачу ленты и правила видимости.
- Заменяем распределённую БД, Kafka и воркеры одним приложением, PostgreSQL и Redis.
- Для автора с не более чем 10 подписчиками запись поста добавляется в feed каждого подписчика.
- Для автора с более чем 10 подписчиками (celeb) fanout в PostgreSQL не выполняется; его посты
  хранятся в персональном Redis ZSET и добавляются при сборке ленты подписчика.
- Публикация/изменение/удаление поста фиксируются вместе с событием в `posts_outbox`; отдельный
  воркер применяет события к PostgreSQL fanout-таблице и Redis ZSET.
- Redis ZSET для каждого пользователя кэширует последние 20 fanout-постов из PostgreSQL feed.
- Redis хранит число подписчиков каждого автора с TTL 60 секунд; cache miss считает `follows`.
- Граница 10 — учебное упрощение, не обоснованный масштабный порог; хранить как настройку.
- Ограничения MVP: нет SLA/пиковых гарантий, пагинации снимком и очистки старых строк; outbox-воркер
  опрашивает PostgreSQL с простыми повторами.

## 1. Демо (happy path)

1. Создать 20 пользователей через существующие `/api/v1/auth/register` и `/api/v1/auth/token`.
2. Назначить одному автору 19 подписчиков, чтобы проверить celeb-ветку; остальные тестовые авторы — non-celeb.
3. Загрузить фотографии через API; ручка пишет файл в RustFS, затем создаёт 100 постов со статусом `created` и outbox-событиями.
4. Проверить последние 20 non-celeb постов в PostgreSQL `feed_entries` и Redis ZSET ленты подписчика.
5. Проверить, что celeb посты не попали в `feed_entries`, а все 100 есть в персональном Redis ZSET celeb.
6. Подписчик получает последние посты celeb и non-celeb без дублей, в обратном хронологическом порядке.
7. Удалить пост и отписать пользователя; следующие ответы исключают пост/автора даже при cache hit.

## 2. PostgreSQL

Таблицы описывают SQL напрямую в `app/models.py`. Пользовательская таблица уже существует: добавить
в неё только недостающие поля, сохранив регистрацию и авторизацию шаблона.

```sql
-- уже есть users; auth-поля из существующей схемы оставить
-- добавить недостающее только при необходимости:
ALTER TABLE users ADD COLUMN IF NOT EXISTS created_at TIMESTAMPTZ NOT NULL DEFAULT now();

CREATE TABLE follows (
    follower_id BIGINT NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    followee_id BIGINT NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (follower_id, followee_id),
    CHECK (follower_id <> followee_id)
);
CREATE INDEX ix_follows_followee_id ON follows (followee_id, follower_id);

CREATE TABLE posts (
    id         BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id    BIGINT NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    text       TEXT,
    image_key  VARCHAR(500) NOT NULL,
    status     VARCHAR(20) NOT NULL DEFAULT 'created',
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    deleted_at TIMESTAMPTZ,
    CHECK (status IN ('created', 'published', 'deleted'))
);
CREATE INDEX ix_posts_user_created ON posts (user_id, created_at DESC, id DESC)
    WHERE deleted_at IS NULL;

CREATE TABLE posts_outbox (
    id           BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    post_id      BIGINT NOT NULL REFERENCES posts (id) ON DELETE CASCADE,
    event_type   VARCHAR(30) NOT NULL,
    payload      JSONB NOT NULL DEFAULT '{}'::jsonb,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    processed_at TIMESTAMPTZ,
    attempts     INTEGER NOT NULL DEFAULT 0,
    CHECK (event_type IN ('CREATED POST', 'UPDATED POST', 'DELETED POST'))
);
CREATE INDEX ix_posts_outbox_pending ON posts_outbox (id) WHERE processed_at IS NULL;

CREATE TABLE feed_entries (
    id         BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id    BIGINT NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    post_id    BIGINT NOT NULL REFERENCES posts (id) ON DELETE CASCADE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (user_id, post_id)
);
CREATE INDEX ix_feed_entries_user_created
    ON feed_entries (user_id, created_at DESC, post_id DESC);
```

`feed_entries.user_id` — получатель ленты, `post_id` — публикация. `posts.status='created'` означает,
что пост создан, но outbox-событие ещё может ожидать fanout; воркер выставляет `published` после
применения события. Ключ RustFS хранится как `image_key`.

## 3. HTTP API (`/api/v1`)

Все пользовательские операции защищены `Authorization: Bearer <token>` (`CurrentUser`). Не вводить
CRUD для произвольного `user_id`: идентификатор пользователя берётся из токена.

- `GET /api/v1/users/{user_id}` → `200 {id}`; `404` — пользователь не найден.
- `GET /api/v1/users/{user_id}/followers` → `200 [{follower_id}]`.
- `GET /api/v1/users/{user_id}/following` → `200 [{followee_id}]`.
- `POST /api/v1/users/{user_id}/followers` 🔒 → создать подписку текущего пользователя на `{user_id}`, `201 {follower_id, followee_id}`; повтор → `409`.
- `DELETE /api/v1/users/{user_id}/followers` 🔒 → удалить подписку текущего пользователя, `204`; отсутствующая → `404`.
- `POST /api/v1/posts` 🔒 multipart `file`, `text?` → сначала загрузить файл в RustFS, затем в одной
  PostgreSQL-транзакции создать пост `status=created` и `CREATED POST` outbox-событие; `201 {id, status, image_key, created_at}`.
- `PUT /api/v1/posts/{post_id}` 🔒 multipart `file?`, `text?` → при замене файла сначала записать новый
  объект в RustFS, затем обновить пост и записать `UPDATED POST` outbox-событие.
- `GET /api/v1/posts/{post_id}` 🔒 → `200 {…}`; чужой пост читаем, удалённый или отсутствующий → `404`.
- `DELETE /api/v1/posts/{post_id}` 🔒 → автору записать tombstone и `DELETED POST` событие в одной
  транзакции; `204`, иначе `404`; повторное удаление → `404`.
- `GET /api/v1/feed?cursor=&limit=20` 🔒 → `200 {items: [{post fields}], next_cursor}`; `limit` ограничить диапазоном 1–20.

Пагинация курсорная по `(created_at, id)` в убывающем порядке. Пустая выдача имеет `items: []` и
`next_cursor: null`. Ручки пользователей и списков подписок служат минимальному демо; не раскрывать
пароли или хеши.

Redis ключи: `followers_count:{user_id}` — integer с TTL 60 с; `feed:{user_id}` — ZSET последних 20
fanout-постов; `user_posts:{user_id}` — ZSET всех постов celeb. Везде score — timestamp создания,
member — `post_id`; PostgreSQL остаётся источником истины.

## 4. Важные нюансы

- Для `followers_count:{user_id}` cache miss выполняет `SELECT count(*) FROM follows WHERE followee_id = :user_id`,
  записывает результат с TTL 60 с и по нему выбирает celeb/non-celeb стратегию. Счётчик намеренно
  может устареть до минуты, поэтому при чтении учитываются оба источника, чтобы не терять посты.
- Фото сначала загружается в RustFS. Затем в одной PostgreSQL-транзакции создаются `posts(status='created')`
  и `posts_outbox(CREATED POST)`. Если загрузка RustFS не удалась, пост не создаётся. Если запись БД
  упала после успешной загрузки, объект может остаться orphan; MVP не удаляет его автоматически.
- Outbox-воркер постоянно опрашивает необработанные события по `id`, применяет их идемпотентно и
  только после успешного обновления feed/Redis отмечает `processed_at`, увеличивая `attempts` при ошибке.
- `CREATED POST`: для автора с ≤10 подписчиками добавить запись каждому подписчику в `feed_entries`
  и обновить их Redis ZSET; для celeb пропустить fanout и добавить пост в `user_posts:{author_id}`.
  После обработки поставить `posts.status='published'`.
- `UPDATED POST`: обновить метаданные/ссылку и timestamp member в PostgreSQL feed и релевантных Redis
  ZSET; событие содержит актуальный snapshot нужных полей.
- `DELETED POST`: endpoint сразу ставит tombstone (`deleted_at`, `status='deleted'`) и outbox-событие
  в транзакции; воркер удаляет post ID из PostgreSQL fanout-строк и Redis ZSET подписчиков/celeb.
  Tombstone делает фильтр немедленным ещё до завершения очистки.
- Повторное событие безопасно благодаря `UNIQUE(user_id, post_id)`, операциям upsert/remove в Redis и
  отметке события только после успешной обработки.
- Для каждого пользователя `feed:{user_id}` кэширует последние 20 fanout-постов из `feed_entries`.
  Cache miss восстанавливает набор из PostgreSQL; кэш не заменяет таблицу-источник.
- Для автора с >10 подписчиками не создавать fanout-строк. Его `user_posts:{user_id}` содержит всю
  историю опубликованных постов автора в Redis ZSET (в демо — 100); outbox-воркер обновляет набор.
- Лента объединяет feed ZSET и ZSET celeb-авторов, на которых подписан пользователь, затем проверяет
  активную подписку и статус поста, дедуплицирует по `post_id` и сортирует по `(created_at, id)`.
- При потере Redis обычный feed восстанавливается из PostgreSQL, celeb ZSET пересобирается из `posts`.
- Перед ответом проверяются активность поста и текущая подписка автора. Поэтому удаление и отписка
  немедленно убирают результат, даже если в `feed_entries` осталась старая ссылка.
- `GET /feed` включает только `published` посты; `created` ждут обработки outbox, удалённые с tombstone
  исключаются сразу. Физические fanout-записи очищает воркер.
- Только автор может удалить пост. Для простоты не вводить модерацию, приватные аккаунты и блокировки.
- Время ленты — `posts.created_at`, tie-break — `posts.id`; время вставки в fanout не влияет на порядок.
- Ошибки уникальности подписки/вставки преобразовывать в `409`; некорректные поля — стандартный `422`.
- Порог 10 не имеет отношения к исходным звёздным авторам с миллионами подписчиков: это локальная
  настройка учебного MVP, которую нельзя выдавать за решение производительности production-системы.

## 5. Шаги реализации

1. **Схема данных и Redis** — добавить `follows`, `posts`, `posts_outbox`, `feed_entries`, индексы и Redis-клиент;
   миграция применяется успешно, существующая регистрация работает.
2. **Подписки** — добавить просмотр списков, follow/unfollow; curl: подписка возвращает `201`,
   повтор — `409`, отписка — `204`.
3. **Хранилище фото и публикации** — добавить multipart API с записью в RustFS до транзакции поста и
   outbox; curl: успешная загрузка даёт `201 status=created`, RustFS failure не создаёт пост.
4. **Кэш подписчиков** — реализовать Redis cache-aside с TTL 60 с и SQL count при miss; проверить
   выбор стратегии и обновление результата после истечения TTL.
5. **Outbox worker** — обрабатывать `CREATED POST`, `UPDATED POST`, `DELETED POST` идемпотентно;
   curl/демо: после обработки статус `published`, таблица и Redis соответствуют событию.
6. **Сборка ленты** — объединить источники, фильтровать удалённое и отписки, дедуплицировать,
   сортировать и продолжать курсор; проверить cache hit/miss.
7. **demo.sh** — создать 20 пользователей, celeb с 19 подписчиками и 100 постов; проверить последние
   20 записей в PostgreSQL и Redis, полный celeb ZSET и `make demo`.

## 6. Не сделано / риски

- Порог 10 выбран только для задания; production требует подобрать порог по цене fanout и чтения.
- RustFS write перед PostgreSQL может оставить orphan-файл при сбое БД; компенсационная очистка
  объектов не входит в MVP.
- Outbox даёт повторную доставку, но простой воркер без DLQ/метрик может накапливать ошибки и задержку.
- Кэш подписчиков может выбрать устаревшую стратегию до 60 секунд; сборка ленты должна читать оба
  пути, чтобы это не приводило к пропуску постов.
- Redis — восстанавливаемый кэш: обычные ZSET строятся из `feed_entries`, celeb ZSET — из `posts`.
- Один PostgreSQL не подтверждает целевые p95/p99, RPS, доступность и срок доставки 60 секунд.
- Нет фоновой очистки `feed_entries`, rate limiting и ограничений частоты публикаций.
- Размер метаданных, политика хранения постов и URL/срок действия изображений требуют уточнения.
